## Architecture in one paragraph

JPro streams the JavaFX game to the browser over WebSockets. The game keeps
mutable static state (player, FXGL engine), so each player needs their own
JVM. JPro's own load balancer runs a pool of single-player JVMs, and an
Nginx ingress in front of it serves a capacity check and static busy pages,
and blocks the pool's management routes. Browser audio is played by the
player's browser, not the server. Desktop behavior is unchanged. Only the
ingress is ever exposed; the pool must stay private.

Key files: [Dockerfile](../../Dockerfile),
[deploy/compose.services.yaml](../../deploy/compose.services.yaml) (shared, port-free),
[deploy/compose.yaml](../../deploy/compose.yaml) (local, adds a loopback port),
[deploy/compose.dokploy.yaml](../../deploy/compose.dokploy.yaml) (school host),
[deploy/jpro](../../deploy/jpro) (pool config and worker reset),
[deploy/ingress](../../deploy/ingress) (Nginx, capacity check, pages).

  parser tests run during image builds.
- Independent players: separate JVMs, working directories, saves and settings;
  a recycled slot starts with fresh progress. Two games, and a short
  three-game run, were tested.
- Ingress: full pool shows a busy page; management routes return 404;
  ambiguous paths return 400; capacity telemetry fails closed (HTTP 503).
- 20 uninterrupted active-play/disconnect cycles passed on a fresh stack.
- School host: deployed from the branch, trusted Let's Encrypt HTTPS, public
  assets and WebSockets work, one game verified, and the owner played it in
  Brave. Measured one game at about 1.4 GiB average RAM and 0.3 CPU cores

## How to resume

Prerequisites on the owner's Windows machine (user-local, not on PATH):

- JDK 21: `C:\Users\Fran\.local\share\dinosaur-exploder-toolchain\jdk-21\jdk-21.0.12.1+1`
- Maven 3.9.16: `C:\Users\Fran\.local\share\dinosaur-exploder-toolchain\maven-3.9.16\apache-maven-3.9.16\bin\mvn.cmd`
- Docker Desktop with WSL 2 (start it first; its CLI is under
  `%LOCALAPPDATA%\Programs\DockerDesktop\resources\bin`).

Run the local stack (the game at <http://127.0.0.1:8081/>):

```powershell
$env:POOL_ADMIN_KEY=[guid]::NewGuid().ToString('N')
docker compose --project-name dinosaur-local --file deploy\compose.yaml up --detach --build
```

Stop it with `docker compose ... down --timeout 20` (set any non-empty
`POOL_ADMIN_KEY` first; Compose requires the variable). Details, checks and
cautions are in the [container runbook](container.md).

Deploy to the school host: Dokploy dashboard
<https://policloud.ipm.edu.ar> -> project **Dinosaur Exploder** -> service
**browser-staging** -> General -> Deploy. Settings are in the
[Dokploy runbook](dokploy.md). Never put real keys in the repository.

## Testing notes that save time

- The integrated-browser game flow is: click anywhere to start, Start Game,
  choose ship, Weapon, choose weapon, Next, Easy or Normal. Wait about 4.5
  seconds after the HUD appears for the countdown before judging gameplay.
- Hidden browser tabs stall rendering; enable focus emulation through a Chrome
  DevTools session for automated runs. This is a functional aid, not a
  performance measurement.
- Dokploy's own Monitoring pages showed frozen or zero values on the school
  host. Read container counters instead (`/sys/fs/cgroup/memory.current` and
  `cpu.stat`) through Dokploy's service Terminal; choose the pool container
  and Bash.
- Do not print complete container environments, Compose previews with secrets,
  or JPro worker command lines; they can include the admin key.
- Browser-automation page snapshots read the Dokploy environment editor even
  when it is visually masked, so enter secrets by hand.
